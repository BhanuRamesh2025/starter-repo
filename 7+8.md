Step 9: Findings Write-Up
Finding 1: BOLA on /rest/track-order/{id}
Request: GET /rest/track-order/{orderId}
Parameter: orderId in the URL path
What I tried: Logged in as account A, obtained account B’s order ID (cc0a-02366e49465ae2b1) by placing a separate order under account B. Requested B’s order ID while authenticated as A.
What I found: The server returned B’s full order details, masked email, products, pricing, delivery ETA, with no ownership check performed at all.
Severity: High. Leaks PII and order contents across accounts.
Fix in a real app: On every request to this endpoint, verify server-side that order.userId matches the authenticated requester’s user ID before returning data. If guest tracking is a desired feature, require a separate tracking token instead of relying on the order ID.

Finding 2: Broken Authentication, /rest/track-order/{id} ignores the Authorization header entirely
Request: same endpoint
What I tried: Sent the same request with no Authorization header at all, and separately with a malformed/garbage value in place of a token.
What I found: Both returned identical, full order data as a valid request would. The endpoint performs no authentication check whatsoever, it doesn’t matter if a token is present, missing, or invalid.
Severity: High, same underlying endpoint as Finding 1, confirms no auth layer exists here at all.
Fix in a real app: Add authentication middleware to this route requiring a valid session before the handler runs, returning 401 for missing or invalid tokens, the same way /api/Users already correctly does.
